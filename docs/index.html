C++Extended (cxxe)

C++ is powerful, but it carries decades of ceremony: plumbing to observe a variable, boilerplate for getters, fragile macros for converting an enum to a string, and misused destructors to imitate finally.

C++Extended (compiler: cxxe) is a C++ superset that keeps 100% of C++ features and adds a layer of modern ergonomics: decorators, signals, defer, native properties, runtime reflection, and more. The principle is simple: cxxe transforms your extended code into standard C++, without removing anything from the original language.

There is no new language to learn. You simply extend the one you already know.

C++ Compatibility

C++Extended is a superset of C++: any valid C++ code is also valid C++Extended code. An existing project can therefore be migrated file by file.

Extended sources use the .cppe extension; extended headers use .hppe. Plain .cpp / .hpp files pass through untouched, so both kinds can live in the same project.

Command Line (cxxe)

The compiler is a stand-alone executable. It lexes and parses your code itself (it does not call clang, LLVM or any C++ compiler), stores it in an intermediate representation called CPIR, and generates standard C++ from it.

cxxe [options] <command> [arguments]

Commands

CommandDescription
parse <input> <output.cpir>Parses a source file into CPIR and prints the number of nodes and tokens.
emit <input.cpir> <output.cpp>Generates C++ from a CPIR file.
roundtrip <input> <output.cpp>Parses then generates C++ in one step (this is what the CMake toolchain uses). The temporary CPIR file .cxxe.tmp.cpir is removed afterwards.
dump <input.cpir>Displays the contents of a CPIR file (useful for debugging the compiler).
runtime export <directory>Writes cxxe_runtime.hpp and cxxe_runtime.cpp into the directory (created if needed).
runtime header <output.hpp|->Writes only the runtime header. Use - to print to stdout.
runtime source <output.cpp|->Writes only the runtime source. Use - to print to stdout.

Options

OptionDescription
-h, --helpShows the help message.
-v, --versionShows the version (CXXE 0.1).
-I <dir> or -I<dir>Adds an include search directory. May be repeated.

Options must come before the command. Usage errors (unknown option, wrong number of arguments, unknown command) exit with code 2.

cxxe parse main.cppe main.cpir
cxxe emit main.cpir main.cpp
cxxe -I include roundtrip main.cppe generated.cpp
cxxe dump main.cpir
cxxe runtime export ./runtime

Building the Compiler

cxxe is written in C11 with no external dependency. Two build scripts are provided in the Compiler/ folder.

:: Windows (MinGW gcc) - produces cxxe.exe at the repository root
Compiler\Build.bat

# Any platform with CMake
cmake -S Compiler -B Compiler/build
cmake --build Compiler/build

Build.bat accepts an optional output path as its first argument. Self-hosting tests are run with Tests/SelfHost/run.sh (Linux or Git Bash, with gcc/g++ in the PATH).

How cxxe Works

.cppe source -> Lexer -> Parser -> Frontend (includes) -> Sema -> CodeGen -> .cpp
                              |                                  |
                              +---------- Ir (CPIR) <------------+--> IrSerialize (.cpir)

The lexer keeps a lossless token stream (every byte, including whitespace and comments), so unknown constructs survive the round trip unchanged. The generated C++ is byte-for-byte identical to the input for any code that does not use an extension.

Module (Src/)Role
Core/Common includes, memory and diagnostics, string buffer, file I/O, paths and the executable directory.
Lexer/Lossless token model and the C++/CXXE lexer.
Ir/CPIR tree, binary .cpir format (IrSerialize) and the dump command (IrDump).
Parser/Tokens to IR: decorators, custom decorators, expressions, declarations, preprocessor, classes and properties.
Frontend/Resolves #include and imports the declarations of included headers (including the std headers).
Sema/Type and property lookup, native feature resolution, named-argument binding and checks.
CodeGen/C++ generation: named calls, runtime registry, decorators, properties, match, source emission.
Runtime/Embedded runtime sources and the cxxe runtime command.
Driver/Chains the stages (build_ir_from_cpp).
Cli/Help text, error reporting and main.

Properties, constructors and named arguments are recognized while parsing, so declarations from included CXXE headers must be known first. cxxe therefore parses once to discover includes and, if they contribute declarations, parses again with them pre-loaded.

CXXE Headers (.hppe) and Includes

A .hppe header can use every CXXE feature (properties, named arguments, decorators). cxxe translates it to a .hpp, and every #include "x.hppe" is emitted as #include "x.hpp".

Classes, properties, functions and custom decorators declared in included headers are imported before the file is analyzed, so obj.prop = v, f(b=1, a=2) and custom decorators work across files.

Include resolution

  • #include "file": searched relative to the including file, then in each -I directory. An unresolvable quoted include is an error.
  • #include <file>: searched in each -I directory, then in the including file's directory. Unresolved angle includes are assumed to be system headers and are left alone.
  • #include_next and #import are understood; includes built from macros cannot be resolved.
  • Recognized header extensions: .h, .hpp, .he, .hppe, .hh, .hxx, .inl, .inc.
  • The CXXE standard headers live in the std folder next to cxxe.exe and are found automatically, with no -I needed.

Named Parameters

Arguments can be passed by name, in any order.

int add(int a, int b);

int main() {
    int r = add(b=5, a=4);
}

The compiler reorders the arguments to match the declaration and emits a normal call (add(4, 5)). Named calls are resolved against the declarations visible in the file and in its included headers, and nested named calls are supported.

  • An unknown, duplicated or missing argument name is a compile-time error.
  • If no declaration of the function is visible, the call is left untouched (it is then a plain C++ assignment expression) and a warning is printed.

Native Decorators and Reflection

Native decorators allow classes to be registered and members to be exposed so they can be accessed at runtime by name.

DecoratorRole
@registerRegisters the class in the factory.
@exposedExposes a member to reflection. It must be public.
  • @register applies to a named class, struct, union or enum.
  • @exposed applies to a public member variable or a public method (up to 64 parameters).
  • Registration is automatic: cxxe generates a cxxe_generated::register_all() function and a static object that calls it at program start-up.
  • A registered class must be default-constructible to be created through the factory.
@register
class A {
public:
    @exposed int health;
};

Creating Instances

// Instantiate by name
A* obj = std::factory_new("A");

// Same thing, with a "new" syntax
A* obj2 = new std::factory_find("A")();

Both forms are runtime lookups in the class registry; cxxe never replaces the name by the type at compile time. new std::factory_find("A")() is rewritten into std::factory_new("A"), and both are wrapped so the registry is initialized first ((cxxe_generated::register_all(), std::factory_new("A"))). The result converts to A*, and throws if the class is not registered or the type does not match.

Accessing Exposed Members

obj->get_member("health") = 4;

get_member is always a runtime intrinsic, even with a string literal. cxxe rewrites it into std::get_member(obj, "health") (preceded by the registry initialization), which looks the member up by name when the line executes. It is not turned into obj->health.

Exposed methods can be called the same way. The call goes through the runtime registry and returns a std::DynamicValue:

@register
class Player {
public:
    @exposed int health;
    @exposed void heal(int amount) { health += amount; }
};

Player p;
std::get_member(p, "heal")(10);               // runtime call
int h = std::get_member(p, "health");         // runtime read

Reading or writing an exposed member that does not exist, is not registered, or is of the wrong kind (field vs. method) throws a std::runtime_error.

Dynamic Usage

Everything is resolved at runtime: the name can come from a source unknown at compile time.

std::factory_new(unknown_string);
An @exposed member must be public.

Custom decorators

You can declare your own decorators. A decorator receives the decorated function (func) and wraps it as you wish.

void @my_decorator() -> func(int a) {
    before();
    func(a);
    after();
}

A decorator can also take parameters:

void @my_decorator(/* decorator parameters */) -> func(int a) {
    before();
    func(a);
    after();
}

Usage:

@my_decorator
void work(int a) { /* ... */ }

Use func(...) instead of a parameter list to make the decorator accept any function signature:

void @log() -> func(...) {
    std::cout << "call" << std::endl;
    func(...);
}

Templates and namespaces

namespace dec {
    template<typename T>
    void @my_decorator(T a) -> func(...) {
        std::cout << "before" << a << std::endl;
        func(...);
    }
}

@dec::my_decorator<int>(10)
void Show(const char* a) { std::cout << a << std::endl; }

Decorator names are resolved from the innermost scope outward (A::B::dec, then A::dec, then dec). Several decorators can be stacked on the same function (up to 64).

Rules

  • Custom decorators apply to functions and methods with a body only.
  • The number of decorator arguments must match the decorator's parameters, and the number of template arguments must match its template parameters.
  • With an explicit func(int a) target, the decorated function must have the same number and types of parameters.
  • Using a decorator that is neither native nor declared is a compile-time error (unknown decorator).
  • Decorators declared in an included header are imported automatically.
Support for templates on decorators is available.

Lifecycle Decorators

Three standard decorators document the evolution of your API.

DecoratorDescription
@deprecated(msg)Marks an element as deprecated, with a message.
@since(version)Indicates the version in which the element was introduced.
@experimental(msg)Marks an unstable API that may change.
@since("1.2")
@deprecated("Use load_v2() instead")
void load();

@experimental("The interface may change")
void new_feature();

Signals — Abandoned

A signal detects changes to a variable and executes a block of code whenever it changes. It works everywhere: global scope, classes, structures, etc.

int my_int = 0;

signal: my_int {
    var_changed();
}

Inside a class:

class Player {
public:
    int score = 0;

    signal: score {
        update_ui();
    }
};

defer

defer executes a block when leaving the current scope, regardless of the exit path.

void process() {
    FILE* f = fopen("data.txt", "r");
    defer { fclose(f); }

    // ... use f ...
}   // fclose(f) is called here

Inspectable Enums

Enums are introspectable: enum → string conversion, string → enum conversion, and other reflection operations.

@register
enum class Color { Red, Green = 4, Blue };

An enum must carry @register (and be named) to become introspectable. Reflection functions:

FunctionDescription
std::enum_to_string(value)Name of an enum value. Throws if the value or the enum is not registered.
std::string_to_enum<E>(name)Enum value from its name. Throws if not found.
std::enum_has_value(value)true if the value is registered.
std::enum_has_name<E>(name)true if the name exists.
std::enum_names<E>()std::vector<std::string> of all names.
std::get_enum_info<E>()Full EnumInfo (name, type, values).
std::cout << std::enum_to_string(Color::Green) << std::endl;   // Green
Color c = std::string_to_enum<Color>("Green");
bool a = std::enum_has_value(c);
bool b = std::enum_has_name<Color>("Green");
std::vector<std::string> names = std::enum_names<Color>();
auto info = std::get_enum_info<Color>();

Properties (Native Getters/Setters)

Classes and structures natively support properties with get and set, without boilerplate.

class Character {
public:
    int health = 100;

    property health {
        get { return health; }
        set { health = clamp(value, 0, 100); }
    }
};

Usage:

Character c;
c.health = 150;    // calls the setter: health = 100
int h = c.health;  // calls the getter

Rules

  • Properties work in class, struct and union.
  • A property needs a variable with the exact same name in the same type: the property and the variable are the same thing (property health backs int health). Inside the blocks, that name refers to the variable itself.
  • It must contain at least a get or a set block. Inside set, value is the assigned value, typed like the backing field.
  • Supported operators: =, +=, -=, *=, /=, %=, &=, |=, ^=, <<=, >>=, ++ and --.
  • Compound assignments need a getter; ++ / -- need both a getter and a setter; assigning needs a setter.
  • Reads and writes are rewritten into calls to generated get_<name>() / set_<name>(value) methods, everywhere an expression is allowed. Properties declared in included headers work across files.

Output Redirection (IOutput)

All output can be redirected natively, regardless of the mechanism used in the code:

  • std::cout
  • printf
  • std::print
  • and other standard output mechanisms

Redirection is based on the IOutput interface: implement it to send output to a file, an editor console, the network, a log, etc.

#include <ioutput>

The interface lives in the standard library header ioutput (see Standard Library).

CMake Toolchain

C++Extended integrates with CMake through a dedicated toolchain. Extended sources are processed by cxxe before the usual C++ compilation, so the language can be adopted in an existing project without changing the build system.

  • CMake/CXXE.cmake automatically translates the .cppe sources and the .hppe headers found in the target's sources and INCLUDE_DIRS.
  • The generated .cpp is then compiled by your normal C++ compiler.
  • If your code uses reflection, enums, dynamic or match, add the runtime to the build: cxxe runtime export <dir> writes cxxe_runtime.hpp / cxxe_runtime.cpp (C++17 required).

Runtime Library (std)

Features that act at runtime are backed by a small runtime, embedded in cxxe and exported with cxxe runtime export <dir>. It is header-driven (cxxe_runtime.hpp), thread-safe (registries are mutex-protected) and lives in the std namespace.

ElementPurpose
std::DynamicValueImplementation of the dynamic type (is<T>(), as<T>(), has_value()). Built on std::any.
std::Registry, ClassInfo, MemberInfoRegistry of @register classes and their @exposed members.
std::register_class<T>(name)Registers a class (generated for you; .expose_field() / .expose_method() describe its members).
std::factory_new(name)Creates an instance from a class name. Returns a FactoryResult convertible to T* (throws on type mismatch).
std::factory_find(name)Returns the ClassInfo of a registered class.
std::get_member(obj, name)Returns a MemberProxy: assign to write a field, convert to read it, call it to invoke a method.
std::EnumRegistry, register_enum<E>, enum_*Enum reflection, see Inspectable Enums.

Runtime errors are reported as std::runtime_error with a message starting with CXXE: (class not registered, no default constructor, member not found, read-only field, null object, …). as<T>() on the wrong type throws std::bad_any_cast.

Language Server

cxxe-language-server is the shared LSP server for C++Extended. IDE extensions (VS Code, Visual Studio, CLion, …) only act as thin adapters: they register the .cppe language, start the server, connect to it over LSP (JSON-RPC on stdin/stdout) and provide the icon, settings and commands of their IDE.

The server reuses the real CXXE front end (lexer, parser, IR, decorators, properties, named arguments) instead of re-implementing C++, so it understands C++Extended syntax natively and works standalone.

Supported features

  • initialize, shutdown, exit; full document synchronization (didOpen, didChange, didClose);
  • diagnostics: syntax errors, structural errors, invalid decorators, inconsistent properties;
  • documentSymbol and workspace/symbol (open documents), hover, definition, textual references in the current document;
  • completion: general, C++E decorators, C++E members after . / ->, named arguments;
  • signatureHelp and semanticTokens/full.

Building the server

# GCC
gcc -std=c11 -O2 -Wall -Wextra -Werror cxxe_language_server.c -o cxxe-language-server

# Clang
clang -std=c11 -O2 -Wall -Wextra -Werror -Wno-unused-but-set-variable \
  cxxe_language_server.c -o cxxe-language-server
Full semantic analysis of C++ (advanced templates, complete overload resolution, …) is intentionally out of scope. The planned next step is an optional clangd backend: CXXE generates compilable C++, clangd analyzes it, and a source map remaps diagnostics, definitions and hovers back to the original .cppe.

See CXXE_LANGUAGE_SERVER.md for the validation report (18 complex files, GCC/Clang strict builds, ASan/UBSan).

Features in Testing & Roadmap

These features are currently in the testing phase. Their syntax and behavior may still change based on testing and feedback.

Type dynamic (Testing Phase)

A type whose actual type is only known at runtime. A dynamic value can hold values of different types and provides is<T>() for type checking and as<T>() for accessing the stored value.

dynamic value = 42;

if (value.is<int>()) {
    int x = value.as<int>();
    std::cout << "int = " << x << std::endl;
}

value = 3.14f;
std::cout << value.as<float>() << std::endl;

value = std::string("hello");
std::cout << value.as<std::string>().c_str() << std::endl;

dynamic can also be used inside standard containers:

std::vector<dynamic> values = { 42, 3.14f, "hello", true };

for (const auto& value : values) {
    if (value.is<int>())
        std::cout << "int: " << value.as<int>() << std::endl;
    else if (value.is<float>())
        std::cout << "float: " << value.as<float>() << std::endl;
    else if (value.is<const char*>())
        std::cout << "string: " << value.as<const char*>() << std::endl;
    else if (value.is<bool>())
        std::cout << "bool: " << value.as<bool>() << std::endl;
}
Calling as<T>() with a type that does not match the stored value results in a runtime error (std::bad_any_cast).

dynamic is compiled to std::DynamicValue, so the runtime must be part of your build.

Pattern matching (Testing Phase)

A match statement handles a dynamic value according to its runtime type. Inside each branch, value is already treated as the corresponding type.

void Show(dynamic value)
{
    match value
    {
        int:
            std::cout << "Integer: " << value << std::endl;

        float:
            std::cout << "Float: " << value << std::endl;

        const char*:
            std::cout << "String: " << value << std::endl;

        default:
            std::cout << "Unknown type" << std::endl;
    }
}

int main()
{
    std::vector<dynamic> values = { 42, 3.14f, "hello" };

    for (const auto& value : values)
        Show(value);

    return 0;
}
  • The matched value must be a simple variable (not an expression).
  • Each case is a type followed by :; default: or _: is the fallback. At least one case is required (maximum 128).
  • match is lowered to an if / else if chain using is<T>() and as<T>().

JSON, XML, and Other Data Formats

Native facilities for manipulating common data formats (JSON, XML, etc.) directly from the language.

Null Safety

The idea is to turn a null check followed by a call into a safe-navigation call:

if (player) player->update();   // today
player?->update();              // planned

Automatic Serialization

The @serializable decorator will automatically generate serialization and deserialization for a class.

@serializable
class Config {
public:
    int width;
    int height;
};

Notes and Limitations

  • The examples in this documentation illustrate the syntax; the exact names of functions in the std library may vary between versions.
  • An @exposed member must be public.
  • Features marked as “Concept” are not implemented yet.
  • Features that rely on the runtime (@register, reflection, enums, dynamic, match) need cxxe_runtime.hpp and C++17 (std::any).
  • match only accepts a simple variable as its value.
  • Properties require a backing variable with the exact same name in the same type.
  • The language server is not a full C++ semantic engine; it focuses on C++Extended syntax.
